## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2025-02-14 - IP Spoofing Prevention via Utility
**Vulnerability:** Rate limiting endpoints were parsing `request.headers.get("x-forwarded-for")?.split(",")[0]` manually. While Next.js/Vercel correctly sanitizes this so the first IP is the true client, inline parsing scattered across the codebase makes auditing difficult and is risky if the application is migrated off Vercel (where the first IP might be user-spoofable).
**Learning:** Security logic (like IP extraction for rate limiting) should be abstracted into a single, auditable utility. We must also prefer `x-real-ip` when available in Vercel environments. Using the rightmost IP in `X-Forwarded-For` is incorrect as it typically points to the load balancer/proxy closest to the server, leading to DoS.
**Prevention:** Always use a helper function (like `getClientIp` from `src/lib/get-ip.ts`) that prefers `x-real-ip` and abstracts the X-Forwarded-For parsing, ensuring consistent and secure IP resolution.
