## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2026-09-25 - [HIGH] Prevent JSON DoS and SSRF in Webhook Verification
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) parsed the JSON request body before verifying the authentication secret, exposing the server to JSON parsing DoS attacks. Furthermore, if authentication failed, it used the unverified `update.callback_query.id` from the payload to make an external API call to Telegram, creating an SSRF and API spoofing vulnerability.
**Learning:** Webhook authentication must strictly rely on cryptographically secure tokens in headers and must be verified *before* parsing the request body to prevent DoS. Never fall back to inspecting user-supplied payloads prior to validation, and never use unverified payload data to trigger external API calls.
**Prevention:** Always verify secrets before calling `request.json()`. Immediately reject unauthorized requests without using any data from the payload.
