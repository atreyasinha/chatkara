## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2025-02-18 - [CRITICAL] IP Spoofing and Rate Limit Bypass
**Vulnerability:** API routes (`/api/orders`, `/api/admin/login`, `/api/discount`) parsed the `x-forwarded-for` header to extract the client IP for rate limiting without checking for `x-real-ip` first. While Vercel sanitizes `x-forwarded-for` (ensuring the first/leftmost IP is the true client), directly parsing it can be brittle. Furthermore, if a proxy appends its IP, an attacker could spoof IP headers, potentially leading to DoS by using internal proxies as the rate-limited key, affecting all real users sharing that proxy.
**Learning:** Directly parsing `x-forwarded-for` for client IP extraction in serverless environments can lead to rate limiting bypasses or denial-of-service (DoS) via IP spoofing.
**Prevention:** Centralize secure IP extraction using a utility function (`getClientIp`) that prioritizes the `x-real-ip` header (provided securely by platforms like Vercel) over `x-forwarded-for`.
