## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2025-03-09 - [CRITICAL] Rate Limit Bypass via X-Forwarded-For
**Vulnerability:** The application's rate limiting logic in several API routes (e.g., `/api/admin/login`, `/api/orders`, `/api/discount`) extracted the client IP using `request.headers.get("x-forwarded-for")?.split(",")[0]?.trim()`. By taking the first (leftmost) IP in the `X-Forwarded-For` header, the application trusted a value that could be easily spoofed by the client, allowing attackers to bypass rate limits entirely.
**Learning:** In serverless environments behind proxies (like Vercel), the client can forge the leftmost IPs in the `X-Forwarded-For` header. Rate limiting based on this forged IP is ineffective against DoS or brute-force attacks.
**Prevention:** Always extract the client IP securely by prioritizing `X-Real-IP` (often set by proxies) or using the last (rightmost) IP in the `X-Forwarded-For` list, which is appended by the immediate trusted proxy and cannot be forged by the client.
