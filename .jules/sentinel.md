## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.
## 2025-02-18 - [HIGH] Rate Limiting IP Spoofing Vulnerability
**Vulnerability:** The application was manually parsing the `x-forwarded-for` header to extract the client IP for rate limiting by taking the leftmost IP (`split(",")[0]`). This allows attackers to trivially bypass rate limits by injecting a fake `X-Forwarded-For` header in their request, causing their real IP to be appended after the fake one, effectively spoofing the IP seen by the rate limiter.
**Learning:** The leftmost IP in `X-Forwarded-For` is untrustworthy because it is fully controllable by the client. The most trusted IP is the rightmost IP, which is appended by the proxy immediately in front of the application. Furthermore, Vercel provides a specific and trustworthy `X-Vercel-Forwarded-For` header.
**Prevention:** Use a dedicated helper function (e.g. `getClientIp`) that prioritizes trusted headers like `X-Vercel-Forwarded-For` and `X-Real-IP`, and falls back to the rightmost IP of `X-Forwarded-For` when extracting the client IP for security or rate limiting purposes.
