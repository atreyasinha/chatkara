## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.
## 2025-02-27 - Webhook Authorization Check Ordering (SSRF Risk)
**Vulnerability:** The Telegram webhook endpoint (`/api/telegram/webhook/route.ts`) parsed the incoming JSON request body and conditionally executed an outbound API request (`answerTelegramCallback`) using user-supplied data (`update.callback_query.id`) *before* returning a 401 response if the authentication secret was missing or invalid.
**Learning:** This ordering created a severe Server-Side Request Forgery (SSRF) and rate-limiting DoS vector. An unauthenticated attacker could send arbitrary JSON with a valid-looking `callback_query.id`, forcing the application server to make unauthorized outbound requests to Telegram's API on their behalf before failing closed.
**Prevention:** Always verify authentication headers or secrets at the absolute top of the request lifecycle, *before* parsing request bodies (to prevent parsing-related DoS attacks like JSON bombs) or acting upon user-supplied data in any way.
