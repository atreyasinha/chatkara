## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2026-09-14 - [CRITICAL] Webhook SSRF and DoS via Unauthenticated JSON Parsing
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) parsed the user-supplied JSON payload (`await request.json()`) *before* verifying the webhook secret. Furthermore, if the secret verification failed, it used an unverified, user-controlled value from the parsed payload (`update.callback_query.id`) to make an external API call (`answerTelegramCallback`) back to Telegram. This created both a JSON parsing Denial of Service (DoS) risk and a Server-Side Request Forgery (SSRF)/API spoofing vulnerability.
**Learning:** Never parse user-supplied JSON payloads or use unverified user data to execute backend logic/external API calls *before* validating the request's authenticity.
**Prevention:** Always verify cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) in headers *before* parsing the request body. Never fall back to inspecting user-supplied payloads prior to validation.
