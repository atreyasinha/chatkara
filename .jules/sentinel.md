## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass and JSON DoS
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) parsed the JSON body (`await request.json()`) before verifying the authentication secret. If authentication failed, it used the unverified `update.callback_query.id` from the payload to call `answerTelegramCallback`. This exposes the endpoint to JSON parsing DoS and Server-Side Request Forgery (SSRF) / API spoofing by allowing attackers to trigger arbitrary external API calls with unauthenticated user-supplied data.
**Learning:** Always verify authentication secrets (e.g., webhook signatures via headers) *before* parsing the request body. Never use unauthenticated user-supplied data to trigger external API calls or backend logic.
**Prevention:** Move secret verification to the very top of the request handler. Remove fallback logic that interacts with unverified payloads upon authentication failure.
