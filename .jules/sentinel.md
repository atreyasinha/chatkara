## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2026-09-18 - [CRITICAL] Prevent Webhook JSON DoS and API Spoofing
**Vulnerability:** The Telegram webhook parsed the request JSON payload (`await request.json()`) before verifying the secret (`x-telegram-bot-api-secret-token`). This exposed the endpoint to JSON parsing DoS attacks. Further, if the secret verification failed, it still used the unauthenticated `update.callback_query.id` from the payload to make an outbound API call (`answerTelegramCallback`), which is an API spoofing/SSRF vulnerability.
**Learning:** Always verify the cryptographic signature/secret of a webhook *before* parsing its body or using any of its contents. Never use unauthenticated data from a rejected request to perform backend logic or make external API calls.
**Prevention:** Move the `verifyTelegramSecret` check above the `request.json()` parsing, and remove any fallback logic that relies on the unverified payload (like `answerTelegramCallback` for unauthorized requests).
