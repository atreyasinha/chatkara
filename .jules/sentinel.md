## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2025-02-18 - [MEDIUM] Secure Client IP Extraction for Rate Limiting
**Vulnerability:** Rate limiting implementation across API routes relied directly on `request.headers.get("x-forwarded-for")?.split(",")[0]`. If `x-forwarded-for` is spoofed in an environment where it isn't properly sanitized or if internal proxies append to it differently, it can allow a malicious actor to bypass rate limits by injecting a fake IP.
**Learning:** For secure client IP extraction in Next.js/Vercel environments, abstract logic into `getClientIp`. The `x-real-ip` header should be preferred when available because it represents the actual client IP connecting to the edge network and is less prone to spoofing. If falling back to `x-forwarded-for`, remember Vercel safely sanitizes it, meaning the first (leftmost) IP is the true client.
**Prevention:** Always use the centralized `getClientIp` function in `src/lib/get-ip.ts` instead of directly parsing `x-forwarded-for` from request headers.
