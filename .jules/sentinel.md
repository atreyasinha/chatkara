## 2025-02-18 - [CRITICAL] Telegram Webhook Authentication Bypass
**Vulnerability:** The Telegram webhook (`/api/telegram/webhook/route.ts`) verified requests by falling back to checking if the user-controlled JSON payload (`update?.callback_query?.message?.chat?.id`) matched an authorized `TELEGRAM_CHAT_ID` if the `TELEGRAM_WEBHOOK_SECRET` was missing or mismatched. Because webhooks are publicly accessible, an attacker could spoof this JSON payload to bypass authentication completely and update order states (e.g., mark as paid or cancelled).
**Learning:** Never use data from a user-supplied JSON payload as a fallback authentication mechanism for webhooks. Secrets should be enforced strictly.
**Prevention:** Always rely strictly on cryptographically secure tokens (like `x-telegram-bot-api-secret-token`) sent in headers and verified with a constant-time comparison (`timingSafeEqual`) to authenticate webhook calls.

## 2026-10-17 - [HIGH] In-memory Rate Limiter Bypass and O(N) CPU Exhaustion
**Vulnerability:** The in-memory Map rate limiters used `map.clear()` (e.g., in `/api/admin/login`) or simply left the Map at capacity if it was full of recent unexpired requests (e.g., in `/api/orders` and `/api/discount`). The former allows attackers to spam the endpoint to intentionally trigger `.clear()`, instantly resetting rate limits for everyone including themselves. The latter results in unbound Map growth or unbounded memory pruning loops (O(N) operations per request) if the memory is entirely filled with valid recent requests.
**Learning:** Do not use `Map.clear()` when it reaches maximum capacity as a brute force mechanism, and ensure Map bounds are strictly enforced by forcefully pruning the oldest entries if needed to maintain a strict size limit.
**Prevention:** Evict expired entries, and if the Map still exceeds capacity, force eviction of the oldest entries using `map.keys().next().value` to maintain strict capacity limits without dropping all state or introducing O(N) exhaustion loops per request.

## 2026-10-17 - [LOW] Integration Test Environment Variable Checking
**Vulnerability:** The integration tests conditionally skip themselves if `firebaseConfigured()` is falsy. However, the check `process.env.FIREBASE_PROJECT_ID && process.env.FIREBASE_API_KEY` incorrectly evaluates to true in CI environments where these values are replaced with placeholder string secrets like `"***"` or `"dummy"`, leading to failed test suites that depend on a real database instance because the code attempts to communicate with Firebase.
**Learning:** Checking for the presence of environment variables via truthiness (e.g. `Boolean(var)`) is insufficient in environments where sensitive environment variables are sanitized or scrubbed with placeholder strings like `"***"`.
**Prevention:** In test environment configuration checks, specifically verify the expected structure of secrets or explicitly ignore known dummy placeholders (e.g. `process.env.FIREBASE_API_KEY !== "***"` and `process.env.FIREBASE_API_KEY !== "dummy"`).
